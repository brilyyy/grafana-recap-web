# Internationalization (i18n) Technical Notes

## Code Path Utama
- Inlang project config: `project.inlang/settings.json` (`baseLocale: "id"`, `locales: ["id", "en"]`, messages stored as `./messages/{locale}.json`).
- Message sources: `messages/id.json`, `messages/en.json` — flat key → string, `{param}` interpolation.
- Compiler: `pnpm run paraglide` (`paraglide-js compile --project ./project.inlang --outdir ./src/paraglide --strategy cookie preferredLanguage baseLocale`) — generates `src/paraglide/` (has its own internal `.gitignore`, not committed).
- Vite plugin: `vite.config.ts` — `paraglideVitePlugin({ project: './project.inlang', outdir: './src/paraglide' })` recompiles automatically on `vite dev`/`vite build`.
- For non-Vite invocations the compiler is forced via `package.json` `pretype-check` / `pretest` / `prepare` hooks (so `tsc --noEmit` and `vitest run` always see fresh `src/paraglide/messages.js`).
- SSR locale resolution: `src/server.ts` wraps the request handler in `paraglideMiddleware(request, ({ request }) => …)` from `@/paraglide/server` — locale is request-scoped (AsyncLocalStorage), no cross-request bleed.
- `<html lang>`: `src/routes/__root.tsx` calls `getLocale()` from `@/paraglide/runtime` instead of a hardcoded value.
- Switcher: `src/components/language-toggle.tsx` — exports `LanguageRadioGroup` (wired into `settings.tsx`'s appearance card) and `LanguageMenuItems` (wired into `nav-user.tsx`'s dropdown). Both call `setLocale()` from `@/paraglide/runtime`, which persists a cookie and reloads.

## Using Messages in Code
```ts
import { m } from '@/paraglide/messages'

m.common_loading()                 // no params
m.unmapped_count({ count: 5 })     // with {count} interpolation
```
Keys are namespaced by feature prefix (`common_`, `nav_`, `dict_`, `unmapped_`, `analyzer_`, `settings_`, `validation_`, etc.) — grep the prefix before adding a new key, several near-duplicates (e.g. `pagination_page` vs a since-removed `pager_page`) already exist.

## Adding a New Message Key
1. Add the key to **both** `messages/en.json` and `messages/id.json` at the same position (keep them line-aligned where practical).
2. Run `pnpm run paraglide` to regenerate `src/paraglide/messages.js` with the new typed export.
3. Use `m.your_key()` in the component. TypeScript will error if the key is missing from either locale.

## The "Frozen at Module-Import Time" Trap
`m.*()` resolves the **current request/session locale** — but only at the moment it's called. Anything evaluated once at module load (a top-level `const`) freezes whatever locale was active during that first evaluation, and never updates again (including after the user switches locale, since the call already ran).

This affects three common patterns; fix by deferring the `m.*()` call into the render/execution path instead of module scope:

| Pattern | Wrong | Right |
|---|---|---|
| Zod validation schema | `const schema = z.object({ x: z.string().min(1, m.x_required()) })` at module scope | Build it inside the component via `useMemo(() => z.object({ x: z.string().min(1, m.x_required()) }), [])` (cheap to rebuild, locale stays correct since `useMemo` re-runs per mount) |
| Static array/object of labels | `const FLAVORS = [{ description: m.flavor_desc() }]` at module scope | Either call `f.description()` lazily in JSX (store the **function reference**, not its result — see `settings.tsx`'s `FLAVORS`) or move the array construction into a plain function called during render |
| Function default parameter | n/a | `function Foo({ placeholder = m.common_search_ph() }) { … }` is safe — default expressions are evaluated per call, not frozen at module load (see `multi-select-filter.tsx`) |

## Domain-Term Preservation
Some literals stay hardcoded in **both** locales — they are not prose, they're identifiers:
- Domain/business terms: `RC`, `Jenis Transaksi`, status/error-type enum values (`S`, `N`, `Sukses`).
- Data shapes that must stay stable: CSV export column headers (`dictionary-card.tsx`), raw DB column names, example placeholder values (e.g. `"e.g. BRImo"`).

Don't wrap these in `m.*()` — translating an enum value or an export header would break parsing/consumers downstream.

## Voice Guardrails
Friendly, informative, gen-z — but this is a banking-ops dashboard, so:
- Clarity first. Never trade precision for slang.
- Warm, second-person ("kamu" in `id`, "you" in `en`), light and modern.
- Emoji sparingly — empty states and success toasts only, not every string.
- Errors stay plain and direct in both locales (no jokes in error paths).
- Example — `id`: `"Belum ada run — jalanin scheduler-nya, nanti muncul di sini ✨"`; `en`: `"No runs yet — kick off the scheduler and they'll show up here ✨"`.

## Dates
Locale-aware date formatting is centralized in `src/lib/i18n-format.ts` rather than calling
`toLocaleString('id-ID', …)` directly. `localeTag()` maps `getLocale()` to a BCP-47 tag
(`id` → `id-ID`, `en` → `en-US`, fallback `en-US`); `formatDateTime`/`formatDayMonth`/
`formatMonthYear`/`formatMonthName` build on top of it. `superadmin/-shared.tsx`'s
`formatDate()` delegates to `formatDateTime()` so audit logs, processing logs, and user
lists localize consistently.

## Checklist Troubleshooting
1. New key not found / TS error on `m.foo()` → run `pnpm run paraglide`, the generated `src/paraglide/messages.js` is stale.
2. Copy doesn't change after switching locale in Settings → check the string isn't built from a module-level `const` (see the frozen-at-import trap above).
3. SSR renders the wrong locale on first paint → confirm `src/server.ts`'s `paraglideMiddleware` wraps the handler and isn't bypassed by a custom route.
4. `grep -rn "toLocaleString('id-ID'" src` should return nothing — any hit means a hardcoded locale slipped back in.
